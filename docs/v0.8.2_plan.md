## 1. Training speed

### 1a. The adaptive scheduler does not currently work — a real bug

`TaskAdaptiveLossScheduler` (`training/adaptive_callbacks.py:12`) calls
`model.decay_task_weight(...)`, which mutates `self.task_weights[name]`, a **Python
float** (`core/model.py:2914` for the v0.8 head; same pattern at 724, 1366, 2034). That
float is read inside `train_step`, which Keras compiles into a `tf.function` **once per
`fit()` call**. Changing it mid-fit does not retrace, so the compiled graph keeps the
original constant.

Measured on the v0.8 head (`hidden=(32,32)`, 4096 synthetic events, seed 0):

| when `w_ur` is set to 0 | epoch-1 loss | `ur_nll` |
|---|---|---|
| `w_ur=1.0` at construction | 3.3105 | 0.4906 |
| `w_ur=0.0` at construction | 2.8198 | 0.5092 |
| `w_ur=1.0`, decayed to 0 **before** `fit()` | 2.8198 | 0.5092 |

Setting it before tracing moves the loss by exactly the `ur_nll` term (−0.49). Zeroing
it from a callback at the end of epoch 3 of a 6-epoch fit produced **no discontinuity**
at all (2.762 → 2.617 → 2.405 → 2.057, following the same trend as the un-zeroed run).
The callback prints its reduction and updates its state; the graph ignores it.

This affects every model class in the lineage, v0.6 → v0.8, whenever the scheduler is
used *during* a fit. Any earlier result attributed to adaptive weighting should be
re-read as "the constructor weights, held fixed".

**Fix**: store the task weights as `tf.Variable(..., trainable=False)` and read
`.value()` in `train_step` / `test_step`; keep `task_weights` as a property returning
floats so `to_generation_config()`, the monitor and the checkpoint JSON are unchanged.
`set_task_weight` then does `.assign()`. Add a regression test asserting the epoch-N
loss jump when a weight is zeroed from a callback — the test above, kept.

### 1b. What actually costs time, and what would speed it up

CR: 3,443,885 events, batch 4096 → 589 steps/epoch, 76–88 ms/step, **2516 s for 40
epochs**. Small: 1327 s. So the cost is `n_events × epochs`, and the per-step cost is a
small MLP plus the RQS flow — nothing pathological.

Ranked by expected wall-clock return:

1. **Stratified subsampling of the continuum (biggest lever, ~5×).** 3.4M events is far
   past saturation for a 5-output MLP with an 8-dim latent; what needs the statistics is
   the *lines*, which are ≪1% of events. Keep every event inside a line window (±5σ),
   subsample the continuum by a factor `f`, and carry `1/f` in the existing per-event
   sample weights (`build_conditioning_and_weights` already produces a weight vector, so
   the loss path needs no change). Guard: the acceptance harness must be unchanged
   within its thresholds, and the continuum Wasserstein must not degrade — the
   subsampled continuum still has ≫10⁵ events per decade.
2. **Batch size 4096 → 16384.** On CPU this is close to free throughput; costs a
   proportional LR adjustment. Measure, don't assume.
3. **Freeze the geometry heads once they plateau** — the *correct* version of the idea
   in the request. Decaying a task weight to zero still pays the full forward and
   backward cost of that head. Setting `head.trainable = False` removes its gradients.
   Because that changes `self.trainable_variables`, it needs a retrace
   (`self.train_function = None`), which is exactly the mechanism 1a is missing. So 1a
   is a prerequisite for 1c either way.
4. **The scheduler itself (once fixed) is an accuracy tool, not a speed tool.** Decaying
   `ur/uv/phi_r/phi_v` after their NLLs plateau frees the shared trunk to keep improving
   the energy head. It may reduce the *number* of epochs needed, but not the cost of
   one. Worth doing for that reason; do not budget it as a speedup.

The request's premise — that geometry is stable enough to stop optimizing — is
supported: `ur_nll` and `uv_nll` are flat from roughly epoch 10 in the Phase-2 log while
`energy_mixture_nll` keeps improving to epoch 40. That is the plateau the scheduler is
designed to detect.

**Target**: CR 2516 s → under 600 s, with the acceptance table unchanged.

## 3. KL ≈ 27 with `latent_dim=8`

Short answer: **that is not over-compression — it is the opposite**, and it is worth a
diagnostic rather than a change.

KL is the *rate*: the information the latent carries about each event. 27 nats over 8
dimensions is ≈3.4 nats ≈ 4.9 bits per dimension. Over-compression is the low-KL
failure (posterior collapse, KL → 0, the decoder ignoring z). What 27 nats says is that
the encoder is using the latent as an **almost deterministic code** — a per-dimension
rate of 3.4 nats corresponds to a posterior σ of roughly 3% of the prior scale.

Three caveats before drawing conclusions from the number:

- The latent is **8 dims for 5 continuous outputs** (`u_r, u_v, phi_r, phi_v, energy_y`)
  plus the gate. It is over-complete, not a bottleneck.
- With `prior="coupling"`, `kl` is a single-sample **MC estimate** of
  `log q(z|x) − log p(z|cond)` (`core/model.py:3593`), not the closed-form Gaussian KL.
  Its magnitude is not comparable to a `N(0,I)`-prior run, and a learned prior that
  tracks the aggregate posterior can hold a large rate without pathology.
- These are **continuous densities on quantile-transformed variables**, so nats are
  measured against an arbitrary base measure. `rec` is ≈ −22; a rate of 27 × β=0.2 = 5.6
  against that is not extreme.

The genuine risk at high rate is **prior/aggregate-posterior mismatch**: if q(z) does
not tile p(z|cond), generation samples latent regions the decoder never saw, producing
plausible-looking but unphysical events — and with σ_q at 3% of prior scale, there is a
lot of empty space to land in. That is a measurable thing, so measure it:

**Diagnostic (`tools/latent_diagnostic.py`, no training):**
- per-dimension KL decomposition and an **active-unit count** (`KL_d > 0.01`) — if
  fewer than 8 dims are active, the extra capacity is dead weight and the true rate is
  concentrated;
- the histogram of posterior σ per dimension;
- **prior vs aggregate posterior**: encode a validation batch, sample the same count
  from `p(z|cond)`, compare marginals and pairwise 2-D coverage, and report the fraction
  of prior samples falling in regions with no posterior support;
- decoder sensitivity: perturb z by the posterior σ and measure the output shift.

**Then, and only if the diagnostic shows a problem**, sweep `latent_dim ∈ {4, 8, 16}`
and `β ∈ {0.1, 0.2, 0.5}` — scored through `tools/acceptance_v0_8.py`, not by the KL
value. The KL number is not itself a target. If the coverage test is clean, 27 nats is
simply what an 8-dim latent costs to describe this phase space, and the right response
is to leave it alone and say so in the paper.

Note the three sources land at 24.9–28.0. That consistency argues the rate is set by the
data and the β, not by a per-source pathology.

## 4. Error propagation

Nothing in the pipeline currently propagates uncertainty, and the paper will need it.
Four distinct sources, and they need different treatment:

| source | what it is | how to get it |
|---|---|---|
| **Input MC statistics** | the training spectrum is itself one Poisson realization of the Geant4 run | bootstrap: retrain on `B` resamples (or disjoint folds) of the training set, take the spread of the generated spectrum per bin |
| **Training stochasticity** | init, shuffling, latent sampling | multi-seed — already Phase 4 item 17, ≥3 seeds; reuse the same harness |
| **Generation sampling** | finite `n_gen` | analytic: Poisson per bin, known exactly, no runs needed |
| **Model bias** | the residual the model simply gets wrong | not an error bar — it is the acceptance table's job; report it separately and never fold it into a σ |

Practical plan:

1. **State the statistical floor per line first**, because it is free and it reframes
   several existing numbers: a line with `N` real events cannot be validated better than
   `1/√N`. Small's Cu Kα1 has 63 events → a **12.6%** floor, so its recovery of 5.37
   is a real failure, but a recovery of 1.10 would be indistinguishable from 1.0. CR's
   Cu Kβ (thousands of events) is measured far more tightly. Add this column to the
   acceptance table — it tells you which lines the harness can actually adjudicate.
2. **Bootstrap band**: `B = 5` resample-retrains per source is 5 × 42 min for CR under
   today's cost, which is why §1 comes first — after the subsampling lever it is
   plausible in one evening. Report a per-bin ±1σ envelope on the generated spectrum and
   propagate it to the line integrals and to the χ / f_primary normalization factors
   that the Geant4-side `DataAnalysis.ipynb` consumes.
3. **Propagate into the exported source file**: `save_normalization_summary` should
   carry the uncertainty on the normalization alongside the value, so the downstream
   notebook is not silently treating a point estimate as exact.

Cheapest useful subset if time is short: item 1 (free), plus the multi-seed spread
already budgeted in Phase 4, reported as the error bar with the bootstrap flagged as
future work.
