# v0.8.1 — line truth: measurement, line positions, and what the old numbers meant

_Branch `energy-mixture`, 2026-07-27. Companion to `docs/v0.8.1_improvement_plan.md`
(which this partly supersedes — see §1) and `docs/v0.8_v072_comparison.md` (whose
line-recovery tables are superseded outright — see §2)._

This documents the first two phases of v0.8.1: fixing the **instrument** (the
line-recovery metric) and the **physics inputs** (where the lines actually are),
before touching the model's tuning knobs. Both turned out to be broken in ways that
invalidate the line numbers v0.8 has been steered by since Cycle 0.

---

## 1. Why the improvement plan was resequenced

`docs/v0.8.1_improvement_plan.md` §1 proposed, as the primary blocker fix, a
closed-loop calibration of per-line `gate_class_weights` against measured line
recovery. The mechanism is sound and already implemented
(`core/model.py:2734,2809-2820,3656-3663`, persisted through
`to_generation_config`), but three defects sat upstream of it:

| | Defect | Consequence |
|---|---|---|
| **A** | `recovery_ratio = n_gen / n_real` was never normalized for sample size, while the driver capped generation at 1e6 against 3.44e6 (CR) / 1.87e6 (Small) real events | every reported line number deflated by 3.44x / 1.87x |
| **B** | the recovery window was 2 detection bin widths — **±750 eV at 8.9 keV**, 190x the pinned 4 eV FWHM, with adjacent lines' windows overlapping | the "line" count was mostly continuum, and blind to defect C |
| **C** | the candidate table was built from Geant4's `fluor_Bearden` energies, but the simulation emitted **EADL** (`fluor`) energies | every fluorescence line pinned 4-11 FWHM from its real peak |
| **D** | gate targets are Gaussian-soft over the same bin-width bandwidth — **±43 keV at 511 keV**, ±320 eV at 8.9 keV | the gate is trained to route ~10<sup>4</sup> FWHM of continuum into a 4 eV component |

Calibrating per-line weights on top of A-D would have fitted noise. A-C are fixed
here; **D is the next step** (§6).

## 3. Line positions: Bearden vs EADL

`tools/build_candidate_lines_from_geant4.py` read
`G4EMLOW7.3/fluor_Bearden`. Geant4's default atomic-relaxation dataset is EADL
(`G4EMLOW7.3/fluor`) unless the application calls
`SetFluoDirectory("fluor_Bearden")`. Measured directly from
`TrainingData/alloutputDSCryoSphereCR.dat` at 1 eV resolution:

| line | pinned (Bearden) | measured in data | EADL `fluor` | error |
|---|---|---|---|---|
| Al Kα1 | 1.48670 keV | 1.4690 keV | 1.46917 | −17.5 eV = **4.4 FWHM** |
| Cu Kα1 | 8.04778 keV | 8.0055 keV | 8.00571 | −42 eV = **10.5 FWHM** |
| Cu Kβ | 8.90529 keV | 8.8653 keV | 8.86534 | −40 eV = **10 FWHM** |

The measured peaks match EADL to <1 eV. The simulated lines are essentially
monoenergetic — 52,235 of 55,626 events in a 4 keV window around 511 keV fall in a
single 20 eV bin; the Al line sits inside one 4 eV bin — so the 4 eV pinned width is
a deliberate detector-response choice, not a fit, and position accuracy is what
matters.

**Fix.** `--fluor-energy-dir` (default `.../G4EMLOW7.3/fluor`) joins the EADL
energies to the Bearden `.commented.dat` rows on (group header, transition index) —
only the Bearden directory ships the comments that name each transition. Both
energies and their difference are recorded per line, and the output file is tagged
`_EADL` so the Bearden table the earlier checkpoints were trained against is never
overwritten. 66 of 67 instrumental lines move (median −27 eV); the 46 decay lines
are untouched.

### 3.1 Two matching bugs found on the way

**Greedy in-list-order matching.** `detect_energy_lines` looped over candidates in
list order, each claiming the nearest unclaimed peak. Ni Kβ (JSON index 27, 194 eV
away) therefore claimed CR's ~8.0 keV peak before Cu Kα1 (index 28, 23 eV away) was
tried — so **CR's "Ni Kβ" mixture component was really Cu Kα, mislabelled**. Small
labelled the same peak correctly only because its narrower spectrum gives finer bins
and a tighter tolerance. Now assigned closest-pair-first, order-independent.

**Bin centres used as peak energies.** A detection bin is ~166 eV wide at 8 keV and
~21 keV wide at 511 keV on CR's 1024-bin log grid, so the bin centre is not a usable
line position: with closest-pair matching alone, the 511 keV peak (bin centre
509.49 keV) matched **Po-218 at 509.7 keV** instead of the annihilation line. New
`refine_peak_energy()` re-histograms the raw events inside the peak bin at the
detector resolution and returns the centroid of the winning sub-bin; matching then
uses the refined energy. Exposed as `refine_peaks` / `refine_bin_width_mev`.

## 4. The audit

`tools/line_centroid_audit.py` measures, per line, where the real peak is and how
wide it is, straight from the raw events, and compares that with the catalogue value
that would be pinned — reporting the offset in units of the pinned FWHM. It also
flags a line whose measured centroid belongs to a *resolvable* neighbour
(`SHADOWED`, e.g. CR's weak Al Kβ finding Al Kα 76 eV away) and one with no peak at
all (`ABSENT`).

| | CR | Small |
|---|---|---|
| Bearden table | Al Kα2 **4.3**, Al Kβ **22.1**, Cu Kα2 **5.5**, Cu Kβ **10.0** FWHM off → FAIL | Al Kα2 **4.3**, Cu Kα2 **5.5**, Cu Kβ **10.0** FWHM off → FAIL |
| EADL table | 511 **0.0**, Al Kα1 **0.0**, Cu Kα1 **0.0**, Cu Kβ **0.0** FWHM → PASS | 511 **0.0**, Al Kα2 **0.1**, Cu Kα1 **0.0**, Cu Kβ **0.0** FWHM → PASS |

Measured line widths come out at 0.0-0.6 eV, confirming the simulated lines are
delta functions and the 4 eV pin is the intended detector broadening.

## 5. Escape peaks: candidates generated, none confirmed

Requested addition: escape-peak lines from the detector material and the materials
near it. Implemented as:

- `parse_gdml_volume_elements()` maps volume → material → elements, and
  `--detector-volume` selects the detector volumes by name substring. On this mass
  model the defaults match 10 volumes — `SensitiveDetector_Au001` (Au absorber),
  `DetectorPlate_Si001`, five Si CryoAC volumes, `ThermistorCylinder_Ge`, and Cu
  clamps → elements **Si, Cu, Ge, Au**.
- `--escape-peaks` emits `E_parent − E_fluor` for every instrumental parent line and
  every detector-element transition, tagged `origin="escape:<parent>-<element><shell>"`
  and marked `confirmed: null`, into a separate `_EADL_escape` table.

**Result: 358 candidates, 0 confirmed on either source** (CR: 343 absent, 15
shadowed by a true fluorescence line; Small: 344 absent, 14 shadowed). This is the
physically expected outcome and worth stating in the paper: the training data is the
spectrum of particles **crossing a virtual sphere** around the cryostat, not energy
**deposited** in the detector, and an escape peak is a deposited-energy artifact —
the escaping fluorescence photon shows up in this data as its own line, which is
already modelled. A null result, not a failure.

The sweep did surface two real lines not currently modelled: **Pb Kα1 (75.25 keV)
and Pb Kα2 (73.04 keV) in Small**, at 15 and 13 events — below the 100-count
threshold that feeds the mixture head, so they stay out for now.

## 6. Phase 2 — gate-target bandwidth (defect D), fixed and measured

`build_gate_targets` still derives its per-line Gaussian bandwidth from
`match_tolerance_bins` × local bin width, capped at half the nearest-line spacing:
**±43 keV at 511 keV, ±320 eV at 8.9 keV, ±125 eV at 1.49 keV** — 31 to 10,000
detector FWHM. Every event in that neighbourhood is labelled as a line event, so the
gate is *supervised* to over-route by roughly the ratio of the bandwidth to the true
line width, and the mixture then packs all of it into a 4 eV spike while evacuating
the continuum beside it. That is the mechanism behind both the 5-6x over-generation
above and the "digging the between-line continuum" seen in the γ sweeps
(`logs/cycle2_stable_sweep.log`: mode-C core ratio 0.728 → 0.664 → 0.581 as γ rises).

**The fix.** `build_gate_targets` gains `bandwidth_mode="resolution"`: the bandwidth
becomes `bandwidth_sigma * FWHM / 2.3548` from the *pinned line width*, independent
of the binning (scalar, or per line). `continuum_floor` is now mode-aware — with a
few-eV bandwidth, far-from-line events normalize to an all-continuum target whatever
the floor, so the legacy 0.15 would only dilute genuine line events by 13%; the
default becomes 0.02 in resolution mode. Measured on the real data, labelled line
mass over true line fraction:

| | 511 keV | Cu Kα1 | Cu Kβ | Al Kα1 |
|---|---|---|---|---|
| bins mode (v0.8) | 3.45x | 1.26x | 1.83x | 0.89x |
| resolution mode | **0.98x** | **0.99x** | **0.98x** | **0.98x** |

**Synthetic gate.** `tools/synthetic_stress_test_cr_multimodal.py` gained
`--gate-bandwidth-mode` and `--line-sigma-y`; its default lines are 500-1000 eV wide,
a regime the real 4 eV deltas never occupy, so the A/B was run at
`--line-sigma-y 0.002`:

| config | line recovery (4 lines) | between-line continuum | continuum core |
|---|---|---|---|
| bins, γ=2 | 1.08 / 1.69 / 1.46 / 2.57 | 0.43 / 0.16 / 0.30 | 0.655 |
| resolution, γ=2 | 1.21 / 1.69 / 1.49 / 1.69 | 0.90 / 0.51 / 0.30 | 0.562 |
| **resolution, γ=1** | **1.05 / 1.23 / 1.35 / 1.57** | **0.97 / 0.81 / 0.59** | **0.807** |

so v0.8.1 also drops `gate_focal_gamma` 2 → 1: with the labels no longer inflated,
γ=2 over-corrects and digs the continuum beside the lines.

### 6.2 What the run exposed next

- **Cu Kα2 is real, strong, and unmodelled** *(addressed - see §9)*. The near-line continuum check found
  3,945 real CR events (63 in Small) 17-25 eV below Cu Kα1 with essentially none
  generated: that is **Cu Kα2 at 7.98467 keV**, 21 eV from Kα1. Detection cannot
  resolve the doublet (bins are 166 eV wide at 8 keV), so only one of the pair is
  ever matched and modelled. This is the per-ROI fine-detection item: model every
  catalogue line the centroid audit confirms, not only the detection-matched ones.
  Note the same audit must stop treating a doublet member as `SHADOWED` by its
  partner - clip its search window to half the distance to the nearest resolvable
  neighbour.
- **Per-line `gate_class_weights`** for CR 511 (2.45, over) and Al Kα1 (0.32, under),
  and for Small's three lines - with a **two-sided** clip `[1/cap, cap]`, since
  over-generation is the dominant failure (the improvement plan's `[1.0, cap]`
  cannot correct it).
- **CR's 0.02-0.3 MeV continuum** is now slightly *over*-generated (worst
  Wasserstein band, visible in `Plots/v0_8_1_real_CR_spectrum.png`) - the
  Compton-edge knot work from §3 of the improvement plan.
- CR 511's windowed recovery (2.45) exceeds its routing fraction (1.75), meaning
  part of the excess is continuum-flow density piling at 511 keV rather than gate
  over-routing - a small `w_flow_line_repulsion` is the existing lever.

## 9. Cu Kα2 — modelled and measured (v0.8.1 remainder, item 1 of 4)

§6.2 identified Cu Kα2 (7.9847 keV, 21 eV from Kα1) as real, strong (3,940 CR
events), and structurally unmodellable by the existing pipeline: `detect_energy_lines`
bins are 166 eV wide at 8 keV, so a 21 eV doublet is always one bin and only one
member is ever a "detected peak" - no amount of matching-logic improvement fixes
that, because the gap is in peak *detection*, not matching.

**Fix.** `magi.measure_line_centroid` (promoted from `tools/line_centroid_audit.py`'s
`audit_line`, so both share one implementation) measures a candidate directly from
eV-scale events, with its search window clipped to half the distance to the nearest
*resolvable* other candidate (further than one FWHM away). Without the clip, a strong
neighbour's own peak can fall inside the window and win `argmax` - exactly what made
Kα2 read as "shadowed by Kα1" before this fix, despite being a real, distinct line.
`magi.confirm_unresolved_candidate_lines` runs this on every candidate the coarse
`count >= 100` filter didn't already match, and returns matched-line-shaped entries
for the ones confirmed real and strong. `tools/run_v0_8_real.py` and
`tools/acceptance_v0_8.py` call it identically right after the coarse filter.

**A second bug caught before training**: the first version also "confirmed" Al Kα2 as
a separate line. Al Kα1/Kα2 are 0.47 eV apart - the *same* unresolvable peak the
coarse detector already matched as Kα1, not a second line - so
`confirm_unresolved_candidate_lines` now skips any candidate within one FWHM of an
already-matched position. Cu's 21 eV separation clears that bar; Al's 0.47 eV does
not. Both cases are covered by unit tests before touching real data (synthetic
Gaussian doublets with the same separations, at CR-scale counts).

**Real run** (CR only - Small's 63 Kα2 events stay below the 100-count modelling
floor; `trained_models/v0_8_1_cuka2_CR`, `logs/acceptance_v0_8_1_cuka2.json`), 40
epochs, otherwise identical to Phase 2:

| line | Phase 2 (4 lines) | + Cu Kα2 (5 lines) |
|---|---|---|
| e+e− 511 | 2.458 | 2.245 |
| Al Kα1 | 0.315 | 0.322 |
| Cu Kα1 | **1.031 PASS** | n/a (side-band contaminated by Kα2, see below) |
| Cu Kβ | **1.102 PASS** | 0.877 |
| Cu Kα2 | not modelled | n/a (side-band contaminated by Kα1) |

The lines untouched by this change (511, Al Kα1) are unchanged within run-to-run
noise, confirming nothing regressed. Cu Kα1 and Kβ both move slightly against a model
that now has to route a fifth, closely-spaced component - not surprising, and not yet
tuned (that is per-line `gate_class_weights`, item 2 of this queue).

**A second, real bug this run exposed in the metric itself.** Cu Kα1's windowed
recovery first printed as `0.000` - a routing check told a different story
(`component_recovery = 0.727`, a healthy fraction of events assigned to the Kα1 slot),
so this was checked directly: reloading the checkpoint and histogramming *only* the
events the gate routed to the Kα1 component gives mean 8005.70 eV, std 1.64 eV against
a pinned 8005.71 eV / 4 eV FWHM - the model is sampling exactly where and how wide it
should. The `0.000` was `compute_line_integral_recovery` itself: its side-bands (at
2-3× the ±8.5 eV window, i.e. 17-25.5 eV out) are wide enough to reach Kα2, 21 eV away,
so Kα2's *real* line events were being counted as Kα1's *local continuum*, inflating
the subtraction until the line count clipped to zero. This is a genuine limitation of
a side-band continuum estimate once two real lines sit closer together than the
side-band span - not something the old window-only overlap check (radius = the window
itself) could catch, since 21 eV is outside the ±8.5 eV window but inside the
17-25.5 eV side-bands.

**Fixed at the source**: `overlaps_lines`' radius widened to the side-band radius
(a strict superset of the window radius), and a new `sideband_contaminated` flag nulls
`recovery_ratio` when triggered - consistent with how `low_significance` already
nulls a recovery that would otherwise be a spurious number. Verified both directions
on a synthetic doublet (a real line correctly nulled when contaminated; an isolated
line correctly unaffected) before trusting it on the real result above. Both Cu Kα1
and Kα2 now report `n/a` rather than a number that looked like a measurement but
wasn't - `component_recovery` (routing, unaffected by side-bands) is the number to
read for either until they are far enough apart for the windowed metric to trust, or
the metric grows a way to subtract a *known* neighbouring line's contribution from the
side-band instead of just flagging the collision.

**A third finding, incidentally**: `near_line_continuum_ratios`' definition of
"near-line" (the same 2-3× side-band) has the identical blind spot and is not fixed
here - it isn't gated by `compute_line_integral_recovery`'s guards, so its numbers for
closely-spaced lines should be read with the same caveat. One number is worth
surfacing on its own, though: Cu Kα1's near-line continuum ratio was **0.005** before
Cu Kα2 existed as a component (essentially no generated density in that 21 eV gap -
Phase 2's model had no mechanism to place any) and is **0.817** now - direct evidence
that modelling Kα2 fixed a real, severe gap in the generated spectrum, independent of
whatever the windowed recovery metric can or cannot currently measure across it.

**`rebuild_pipeline` in `acceptance_v0_8.py` and `plot_v0_8_real_corr.py`** now takes
the checkpoint's own `model_config["line_positions_y"]` as ground truth for which
lines to reconstruct (matched back to `candidate_lines` by nearest energy), instead of
re-deriving the line set from scratch every time. Independent re-derivation is exactly
what this feature makes fragile: `confirm_unresolved_candidate_lines` can decide
differently on different days (a future GDML update, a new candidate line), and an old
checkpoint's line count would then silently disagree with what the harness rebuilds -
wrong gate-target shape, not a clean error. Verified against both directions: scoring
the *old* 4-line `v0_8_1_CR`/`v0_8_1_Small` checkpoints through the updated
`acceptance_v0_8.py` reproduces the Phase 2 numbers in the table above to three
figures, and the *new* 5-line checkpoint scores cleanly with no shape mismatch.
`acceptance_v0_8.py` also gained `--run-tag` (default `v0_8_1`) for this reason - it
had none before, so it could never have pointed at a `run_v0_8_real.py` checkpoint
under any tag other than a literal, undocumented one.

**Next in this queue**: per-line `gate_class_weights` (CR 511 over-generated,
Al Kα1 under; Small's three lines) - the improvement plan's original goal, now with a
genuine, trustworthy per-line signal for the first time. Then Phase 3 (continuum
polish, which is also where the near-line-continuum blind spot above likely belongs)
and Phase 4 (release hardening).

## 10. Per-line `gate_class_weights` (v0.8.1 remainder, item 2 of 4)

### 10.1 Which signal to calibrate against, and which lines not to touch

`compute_line_integral_recovery` returns two numbers per line: the windowed
`recovery_ratio` and the routing-based `component_recovery`. They can disagree - CR
511's windowed recovery (2.245) exceeds its routing fraction (1.717) - because the
window just counts generated events in an energy slice, regardless of which mixture
component produced them, while routing counts only the events the *gate* assigned to
that line's slot. `gate_class_weights` acts on the gate's auxiliary loss, so it can
only move the routing number; the gap between the two (≈0.53 of CR 511's excess) is
the continuum flow itself placing density at 511 keV independent of gate routing, and
needs a different lever (`w_flow_line_repulsion`, already in the model). Calibrating
against the *windowed* number would overcorrect the routing to compensate for a defect
this knob cannot reach. **`component_recovery` is therefore the calibration target.**

Two lines are excluded regardless: **Cu Kα1 and Kα2 on CR**, both flagged
`sideband_contaminated=True` (§9). `component_recovery`'s denominator
(`real_fraction_line`) is computed from the same side-band subtraction that clips
`recovery_ratio` to `None` for these two - it just isn't nulled in the same way, so it
silently reports a number (Kα1: 0.757) built on a compromised measurement (`n_real_line
= 3604`, against the clean eV-resolution count of 7542 for Kα1 alone - roughly half).
Calibrating against that would tune the model against a measurement artifact, not the
model's real behaviour. Left at the neutral weight until the metric itself learns to
subtract a *known* neighbouring line's contribution instead of just flagging the
collision. Cu Kβ (routing 0.872) already passes acceptance and is left untouched too -
only genuine failures are corrected.

### 10.2 Which direction, and why (worth writing down - it is not the obvious one)

The auxiliary gate loss is `gate_aux_loss = -sum_i w_i * gate_target_i *
log(pooled_gate_i)` (`core/model.py`, the `gate_ce = gate_ce * self._gate_class_weights`
line). The naive intuition - "give a mismatched slot more weight to force it toward
the target, regardless of which way it's currently wrong" - is backwards. Minimizing
`-sum_i w_i * t_i * log(p_i)` over a simplex `p` (Lagrange multiplier λ for `sum p_i =
1`) gives `w_i t_i / p_i = λ` for every `i`, i.e. **`p_i* = w_i t_i / sum_j(w_j t_j)`
at the optimum - the equilibrium routing fraction scales *proportionally* with `w_i`**,
not toward `t_i` regardless of `w_i`. So to *reduce* an over-routed line's fraction,
its weight must *decrease*; to raise an under-routed one, its weight must *increase* -
matching the earlier assessment that a one-sided `[1.0, cap]` clip "cannot correct"
over-generation (§1 of the original improvement plan) and motivating the two-sided
`[1/cap, cap]` clip used here.

Since `p_i ∝ w_i` (to first order, the ≈99% continuum slot dominates the denominator
sum, so a single line's weight barely moves it) and `component_recovery = p_i /
t_i` is what we want to bring to 1, the correction is `w_new = w_old * (1 /
recovery)`, damped by `alpha=0.5` since this is one calibration step against an
idealized-equilibrium argument, not a closed-form solve of the actual finite-capacity,
finite-training optimization:

```
w_new = clip(w_old * (1 / component_recovery)^alpha, [1/cap, cap]),  alpha=0.5, cap=8
```

### 10.3 Calibrated weights (from `logs/acceptance_v0_8_1_cuka2.json` / Small's
regression report, `w_old = 1.0` throughout - no prior calibration exists)

| source | line | routing (component_recovery) | `w_new` |
|---|---|---|---|
| CR | e+e− 511 | 1.717 (over) | **0.7631** |
| CR | Al Kα1 | 0.322 (under) | **1.7613** |
| CR | Cu Kα1 / Kβ / Kα2 | — | 1.0 (untouched, §10.1) |
| Small | e+e− 511 | 0.555 (under) | **1.3424** |
| Small | Al Kα2 | 3.824 (over) | **0.5114** |
| Small | Cu Kα1 | 5.242 (over) | **0.4368** |

None hit the `[1/8, 8]` clip - `alpha=0.5` keeps this first calibration step inside a
reasonable range on both sources. Implemented as `GATE_CLASS_WEIGHTS_BY_LABEL` in
`tools/run_v0_8_real.py`, keyed by label (not position) so it reads directly against
the table above and does not depend on `matched`'s order; any label not listed
defaults to the neutral 1.0, which is how Cu Kα1/Kβ/Kα2 stay untouched without special
casing.

### 10.4 Result: it does not work. Reverted.

Both sources retrained 40 epochs with the table above
(`trained_models/v0_8_1_gatew_{CR,Small}`, scored by `tools/acceptance_v0_8.py`).
Routing before → after, with the **implied response exponent β** where
`routing_ratio = w^β`:

| source | line | `w` | routing before | routing after | ratio | β |
|---|---|---|---|---|---|---|
| CR | e+e− 511 | 0.7631 | 1.721 | 1.424 | 0.827 | 0.70 |
| CR | Al Kα1 | 1.7613 | 0.319 | 0.381 | 1.192 | 0.31 |
| CR | **Cu Kβ** | **1.0 (control)** | **0.893** | **1.129** | **1.265** | — |
| Small | e+e− 511 | 1.3424 | 0.557 | 2.180 | 3.916 | 4.64 |
| Small | Al Kα2 | 0.5114 | 3.814 | 2.088 | 0.548 | 0.90 |
| Small | Cu Kα1 | 0.4368 | 5.274 | 3.484 | 0.661 | 0.50 |

**The control line is the decisive number.** CR's Cu Kβ had its weight left at
exactly 1.0 and still moved **+27%** between the two runs - *more* than either
deliberately-weighted CR line moved (−17%, +19%). The two runs differ only in two
*other* lines' loss weights, so that +27% is pure run-to-run variance. On CR, the
calibration's effect is therefore **not distinguishable from noise**.

**And the response has no stable gain.** β spans 0.31 → 4.64 across the five
weighted lines, a 15× range, with no pattern by source, energy or line strength.
There is nothing to iterate on: a second correction computed from these numbers
would be fitting noise.

**Small's 511 is the clearest failure.** It was under-routed at 0.557 (error 0.44
below target); a 1.34× weight sent it to 2.180 (error 1.18 *above*). Right
direction, ~3× worse in absolute error.

Global metrics moved against us too - coupling residuals degraded on both sources
(CR 0.0415 → 0.0497, essentially at the 0.05 threshold; Small 0.0232 → 0.0429,
nearly doubled), Small's Wasserstein worsened slightly (0.00668 → 0.00751), and CR's
improved (0.02387 → 0.01986). **No line changed its acceptance verdict on either
source.**

**Why the §10.2 argument failed.** It solved for the optimum of the gate CE *in
isolation*. The gate CE is one term among several competing for the same density -
the mixture NLL is the dominant reconstruction term, the gate CE carries
`w_gate_aux=2.0` against it, and the continuum flow can place density at a line's
energy without the gate's involvement at all. β<1 on CR is that competition damping
the gate; β=4.6 on Small is something else dominating entirely. The knob is a soft
nudge on one term, not a controller with predictable gain.

**Reverted** to neutral weights: `GATE_CLASS_WEIGHTS_BY_LABEL = {}` in
`tools/run_v0_8_real.py`, with this result recorded there. The plumbing is correct
and tested - only the calibration is withdrawn. `trained_models/v0_8_1_cuka2_CR`
(§9) remains the best CR checkpoint.

### 10.5 What this changes about the plan

**Multi-seed becomes a prerequisite, not a follow-up.** It currently sits in Phase 4
(item 17). This result promotes it: a per-line effect of ±20% cannot be calibrated
against a measurement whose run-to-run noise is ±27%, and *we only know that number
because CR happened to have two untouched lines acting as an accidental control
group.* Small had none - all three lines were weighted - which is why its 511
result is uninterpretable in isolation. Any future per-line tuning needs the noise
floor per line first, and any future A/B of this kind should deliberately leave a
control line unweighted.

**Al Kα1's under-generation is not noise, and probably is not a gate problem.** It
sits at 0.315 / 0.319 / 0.318 across three independent runs before weighting - far
too stable to be variance - and boosting its weight 1.76× moved it only to 0.381. It
is also at 1.469 keV, inside CR's **worst** Wasserstein band ([−3.41, −1.88) in
log₁₀(E/MeV) = 0.39–13.2 keV, W=0.105, ~5× the global 0.020). Every CR fluorescence
line lives in that band. Tuning a gate to place lines correctly on a continuum that
is itself the worst-fit region of the spectrum is treating the symptom - **Phase 3
(continuum polish) should come before any further line-level tuning**, and may move
these lines on its own.

**Recommended order from here:** Phase 3 (continuum, esp. the 0.39–13.2 keV band)
→ multi-seed (noise floor, ≥3 seeds) → revisit per-line weights only if a gap
survives both, with a control line held out.

### 11.1 Splitting the two levers: the hypothesis above was wrong

Ran each lever alone on CR (`--continuum-flow-bins`/`--warp-boost-cr` added to
`run_v0_8_real.py` for exactly this), against the same `v0_8_1_cuka2_CR` baseline:

| metric | baseline | bins 24→32 only | knot boost only | both (§11) |
|---|---|---|---|---|
| target [−3.41,−1.88) | 0.1177 | 0.1174 (−0%) | **0.0888 (−25%)** | 0.1344 (+14%) |
| global | 0.0235 | 0.0264 (+12%) | 0.0262 (+11%) | 0.0288 (+23%) |
| [−1.88,−0.35) | 0.0288 | 0.0257 (−11%) | 0.0297 (+3%) | 0.0397 (+38%) |
| [−0.35,1.18) | 0.0498 | 0.0557 (+12%) | 0.0656 (+32%) | 0.0568 (+14%) |
| [1.18,2.71) | 0.0070 | 0.0066 (−6%) | 0.0046 (−34%) | 0.0098 (+40%) |
| [2.71,4.24) | 0.0075 | 0.0061 (−20%) | 0.0086 (+14%) | 0.0084 (+12%) |
| high-E/muon guard [4.24,5.77) | 0.0202 | **0.0173 (−14%)** | **0.0115 (−43%)** | **0.0294 (+45%)** |
| coupling max\|Δcorr\| | 0.041 | 0.037 (−10%) | **0.025 (−39%)** | 0.048 (+17%) |

**Neither lever alone reproduces the damage.** `bins32` alone is roughly a wash
(mild global regression, everything else flat or better, guard band and coupling
both improved). `knot-boost` alone is the best single result seen in Phase 3: the
targeted band improved 25%, the guard band improved 43%, coupling improved 39% -
at the cost of two untargeted bands worsening (+32%, +14%). **Combined, the two
were worse than either alone on all four headline numbers** (target, global, guard,
coupling) - not merely additive, actively worse.

This rules out the §11 hypothesis (CR struggling with more spline bins). What's
left is a real non-additive interaction between the two changes, or - equally
possible with only one seed per configuration - four single stochastic draws whose
spread is large enough to produce exactly this pattern by chance. The swings here
(11-43%) are the same order of magnitude as the ±20-27% per-line noise floor
established in §10.5, and none of these four runs has a second seed. **This cannot
be resolved without multi-seed data**, which is already queued ahead of further
line-level tuning for the same reason.

**Not adopted yet, despite the promising single boost-only number.** Best next
step if this is picked back up: run the boost-only config on a second seed before
treating a 25%/43%/39% single-run improvement as real. `trained_models/v0_8_1_cuka2_CR`
remains the reference checkpoint. Evidence checkpoints:
`trained_models/v0_8_1_phase3_bins32_CR`, `trained_models/v0_8_1_phase3_boost_CR`.

### 11.2 Second seed on boost-only: does not replicate - and the reason is worse than a miss

Ran the boost-only config again, `--seed 7` (data split stays `random_state=42`
regardless - only weight init / training stochasticity differs; confirmed identical
319-knot warp grid and matched line list in the logs):

| metric | baseline | boost seed42 | boost seed7 | seed42→seed7 |
|---|---|---|---|---|
| target [−3.41,−1.88) | 0.1177 | 0.0888 | 0.0296 | **−67%** |
| [−1.88,−0.35) | 0.0288 | 0.0297 | 0.0452 | +52% |
| [−0.35,1.18) | 0.0498 | 0.0656 | 0.0076 | **−88%** |
| [1.18,2.71) | 0.0070 | 0.0046 | 0.0082 | +77% |
| [2.71,4.24) | 0.0075 | 0.0086 | 0.0103 | +20% |
| guard [4.24,5.77) | 0.0202 | 0.0115 | 0.0094 | −18% |
| global | 0.0235 | 0.0262 | 0.0227 | −13% |
| coupling | 0.041 | 0.025 | 0.031 | +24% |
| e+e− 511 routing | ~1.7-1.8 (FAIL, over-gen) | 1.796 (FAIL) | **0.467 (PASS)** | qualitative flip |

**This is not "the improvement didn't hold up" - it's that the per-band Wasserstein
metric itself is far noisier than anything assumed so far.** −67% to +77% swings
between two seeds of the *identical* config dwarf the ±20-27% per-line noise floor
established in §10.5 (which was measured on routing ratios, a different and
apparently much more stable statistic - global Wasserstein and coupling here only
moved 13-24% between seeds, in line with that floor). The target band looks
*better* on seed 7 than on seed 42 (0.0296 vs 0.0888, both far under the 0.1177
baseline) - which sounds like an even stronger win, except there is no seed-7
*baseline* (no-boost) run to compare it against, so this could equally be what
seed 7 does to the unmodified architecture. Without that fourth cell (2x2: seed
x boost) the boost's effect cannot be separated from seed variance at all.

**Conclusion: no claim about the knot-boost mechanism (helps, hurts, or neutral)
is currently supportable.** The single-run evidence in §11 and §11.1 that looked
like a finding was, at the per-band level, largely noise. This raises multi-seed
from "prerequisite for the next round of line-weight tuning" (§10.5) to
"prerequisite for interpreting *any* single Phase 3 run, including the ones
already done here." Recommendation: stop spot-checking individual seeds and build
the actual multi-seed harness (Phase 4 item 17: >=3 seeds per config, mean +/- std
through `acceptance_v0_8.py`) before drawing further conclusions from continuum
changes - the per-band Wasserstein diagnostic that motivated this phase in the
first place should be reported as mean +/- std over seeds, not a single run, from
here on.

### 11.3 Three seeds each, properly: the knot boost has no detectable effect

each seed's checkpoint dir the same way `run_v0_8_real.py` names them). Filled out
the grid: baseline (`v0_8_1_cuka2`, no boost) and boost (`v0_8_1_phase3_boost`),
each at seeds 42/7/13 on CR (seed 42 for both already existed; trained seeds 7 and
13 for baseline, seed 13 for boost - four more full CR runs).

| metric | baseline (n=3) | boost (n=3) | diff | combined std | \|diff\|/combined std |
|---|---|---|---|---|---|
| target [−3.41,−1.88) | 0.0778 ± 0.0342 | 0.0832 ± 0.0428 | +0.0054 | 0.0547 | **0.10** |
| global | 0.0227 ± 0.0042 | 0.0267 ± 0.0040 | +0.0040 | 0.0058 | **0.69** |
| guard [4.24,5.77) | 0.0217 ± 0.0029 | 0.0154 ± 0.0084 | −0.0064 | 0.0089 | **0.72** |
| coupling | 0.034 ± 0.005 | 0.028 ± 0.002 | −0.006 | 0.0054 | **1.11** |

**None of the four reach even 1.5 sigma of combined noise - the boost's effect,
if any, is not distinguishable from run-to-run variance.** The target band -
the one metric this whole exercise was trying to move - has essentially zero
signal (0.10 sigma) and its baseline mean (0.0778) is actually *higher-variance*
than its single-seed value from §11 (0.1177) suggested; the boost mean (0.0832) is

result in §11.1. Global and coupling show a mild, consistent-looking improvement

conclusive at n=3 per arm - a real effect at this scale would need roughly an

deviations are relative to the means (the target band's std is 40-50% of its

**Decision: do not adopt the CR knot boost.** `WARP_BOOST_RANGES_BY_SOURCE = {}`

`--continuum-flow-bins` remain available as opt-in flags for anyone who wants to
revisit this with more seeds. `trained_models/v0_8_1_cuka2_CR` remains the sole
reference checkpoint.

**The larger lesson is about the diagnostic, not the fix.** Per-band Wasserstein
on CR has a standard deviation comparable to or larger than most effect sizes
worth chasing in this project. Any future continuum-polish claim on CR needs to be
reported as mean +/- std over >=3 seeds from the start, not eyeballed from one
run - single-run "improvements" of 25-45% (§11, §11.1) turned out to be smaller
than the metric's own seed-to-seed noise. This should also inform how the go/no-go
bar itself is read: a single-run PASS/FAIL on `acceptance_v0_8.py`'s per-band
numbers is not by itself strong evidence of anything at the band level, even
though the aggregate/global metrics (global Wasserstein, coupling) are
comparatively stable (13-24% seed-to-seed swing, matching the ±20-27% floor
already established in §10.5 from routing ratios) and can be trusted more.

Ran the same 3-seed grid on Small's baseline (`v0_8_1`, seeds 42/7/13 - no lever

|---|---|---|---|---|
| global | 0.00670 | 0.00653 | 0.00056 | **8.6%** |

## 12. Phase 4 (release hardening): config-match guard, minimal CI, and a real Geant4-export bug

### 12.1 Config-match guard

`training/checkpointing.load_task_adaptive_model_for_generation` used to rebuild
the v0.8 mixture head entirely from `model_config.get(key, <default>)` - a
missing or renamed key (schema drift between when a checkpoint was saved and
when this loader is run) silently produced a *different* architecture instead
of an error, and the three most dangerous fallbacks
(`continuum_mode="gaussian"`, `prior="gaussian"`, `continuum_flow_warp="affine"`)
select a code path rather than a layer shape, so they do not reliably fail
`load_weights`'s shape check either - the checkpoint loads "successfully" with
weights that no longer mean what they did at training time.

Added `_V08_MIXTURE_REQUIRED_KEYS`: every key
`CVAE_MixEnergy_ContPhi_TaskAdaptive.to_generation_config()` emits, checked
up front; any missing key raises `ValueError` naming it. `to_generation_config()`
also now stamps `config_version=1`. Verified against all 19 v0.8-mixture
checkpoints already in the repo (all pass - `to_generation_config()` always
wrote the full key set, so no existing checkpoint is affected) plus a
deliberate missing-key repro that now raises instead of silently drifting.

### 12.3 A real bug this caught: Geant4 export was broken for every v0.8/v0.8.1 checkpoint from `run_v0_8_real.py`

Writing the Geant4-export test (prompted by a direct request to verify the
Geant4 script + macro integration still works) found that
`scripts/generate_geant_source.py` - what a Geant4 macro's `/generator/mlScript`
invokes - was broken for every checkpoint this session's `tools/run_v0_8_real.py`
had produced (all of §9-§11.4's evidence checkpoints included). Two omissions,
both silent until export was actually attempted:

1. `save_final_trained_model(...)` was called without `preprocessing_metadata`,
   which defaults to `{}`. `generate_geant_source.py` immediately does
   `preprocessing["idx_to_type"]`, `preprocessing["type_probs"]`,
   `preprocessing["n_types"]` with no `.get()` fallback - `KeyError` on an
   empty dict.
2. No `*_quantile_transformers.joblib` was saved alongside the checkpoint (the
   fitted `qt_u_r`/`qt_u_v`/`qt_phi_r`/`qt_phi_v` the export script needs to
   invert geometry back to physical units) - would have been the next failure
   even past (1).

`MAGI_v0_8_1.ipynb`'s own checkpoint-save cell already does both correctly
(it was the reference used to fix this); `tools/run_v0_8_real.py` is a
training/scoring-only driver written for this session's experiments and never
carried that logic over. Fixed by building the same `preprocessing_metadata`
shape (source, geometry_transform, energy_transform, energy_bins, type_probs,
idx_to_type, n_types, radius, center) from locals already in scope and dumping
`feature_pack["quantile_transformers"]` next to the weights - see the comment
at the checkpoint-save block in `tools/run_v0_8_real.py`.

Verified end-to-end with a tiny synthetic checkpoint: built the same way,
`scripts/generate_geant_source.py` invoked as a real subprocess (exactly how
a Geant4 macro calls it), in both `--format text` and `--format binary`,
producing a valid particle file (8 columns - ParticleName, Energy, X, Y, Z,
Vx, Vy, Vz - matching the documented convention). This is now
`test_geant4_export.py`, so the check runs on every future change instead of
needing a manual repro.

**Not done:** the already-saved checkpoints from this session (`v0_8_1_cuka2_CR`,
the Phase 3 grid, the Small multi-seed grid, etc.) were not retroactively
patched with `preprocessing_metadata`/the joblib file - none of them are
referenced by a live Geant4 macro (the `try.mac` files found on disk all point
